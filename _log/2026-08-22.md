### Docker notes
The basic set up of a docker file is the following:
```
FROM    - the base image
WORKDIR - the working directory within the image
COPY    - copies source code into the image, although this 
          can also be used for multistage builds.
RUN     - build time instructions. specifies the necessary commands 
          to run the application within the container.
CMD     - what runs when the application starts 
EXPOSE  - determines which port the application is expected to use.
```  

Building Docker is like so (note the `.` at the end: that is the build context):
```
docker build -t <container-reference-name> . 
```
whereas running Docker becomes a little more complicated:
```
docker    run
          -d (detaches container)
          -p (sets the ports - host port:container port)
          image (the image being run)
```
Most useful command here: `docker ps`. Allows for the listing of all active containers. Stop a container with `docker stop <alias>` and remove it using `docker rm <alias>`. I remember going through this on DataCamp two years ago and wondering why it took so long for the course to discuss using aliases!

To update an image, 
1. Make a change to the source code,
2. Rebuild the image, 
3. Stop+remove the containers that are active,
4. Restart the containers. 

**Persistent memory is important** and something that wasn't covered in my notes two years ago. You can create an external persistent source using `docker volume create <volume-name>`. This is a store of memory that can be used to store databases and the like. They're mounted via the run command like so:
```
docker    run
          -d (detaches container)
          -p (sets the ports - host port:container port)
          -mount
          type=volume,src=<volume-name>,target=<loc-in-image> 
          name (name of process)
```
You can also use `type=bind` to situations where you need to link a direct source of memory in your system with the docker container. One very important way that this is carried out is for CI/CD: bind allows fast updates with live reload. 

You can create networks between containers with `docker network create <network-name>`. the most appropriate way to organise all of this, however, is to use `docker compose`. The basic structure of a compose file (`compose.yaml`) is
```
services:
  app:
    build: .
    image: my-app:latest
    command: python app.py
    ports:
      - "8000:8000"
    working_dir: /app
    volumes:
      - app-data:/app/data
    environment:
      DATABASE_URL: postgresql://database/app
    depends_on:
      - database

  database:
    image: postgres:latest
    volumes:
      - db-data:/var/lib/postgresql/data

volumes:
  app-data:
  db-data:
```

This is run using `docker compose up -d` and deactivated via `docker compose down`. An important tool here is `docker compose logs -f`: this provides tracking capabilities for the network of components. You can also use compose to simplify the rebuilding process with the command `docker compose up -d --build`.

Finally, an important and very powerful means of using Docker is the possibility of multistage builds. This is where you use intermediary containers to build necessary parts of the application without having to include those parts into your full final container. The main essence here is to employ a set of lines in your Dockerfile:

```
FROM image AS alias
...
COPY --from=alis /path/ /loc/
```

You can also build layers selectively using `build`. 
```
docker build --target builder
```
This would execute until the builder stage.
