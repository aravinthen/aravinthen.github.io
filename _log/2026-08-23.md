### FastAPI
1. `FastAPI` Calls itself a modern, fast web framework for building APIs. It uses Python type-hinting heavily for strict input validation (alongside `pydantic`). `FastAPI` is foundationally a means of allowing different applications to interface with eachother in a safe way. 
2. What makes it so useful for ML engineers?
    1. The first use-case I can come up with is the strict data validation that comes with the `pydantic` side. Prevents your machine learning model from getting strings when it wants floats.
    2. Oh, of course: the second usecase is to actually convert your machine learning model into a usable service. I put a bit more investigation into this just to clarify some more technical terms:
        * The model is exposed via a REST API viewpoint. All that means is that anybody who has access to the webpage where the model is hosted can send inputs and then get a prediction back.
        * `FastAPI` also removes the need for loading weights each time a model is used. It allows engineers to keep models working in the background.
        * Specifically, `FastAPI` allows for a `POST` endpoint. `POST` is a means of sending information safely to a server.
    3. I'm guessing the essence of this usecase is the following:
        * A user sends data to the endpoint.
        * FastAPI intercepts it, feeds it directly into the model waiting in the RAM.
        * The model instantly calculates the answer.
        * FastAPI sends that answer back to the user over the internet.

### Pydantic
1. It seems as though `pydantic` is an essential part of what makes `FastAPI` a powerful piece of kit for machine learning in particular. 
2. This is a means of *deeply enforcing data schemas*. I get the impression that the basic role of `pydantic` is to essentially force validation under all conditions. 
3. I'm seeing a pretty basic essential usage pattern here:

#### Define typed models by inheriting from `BaseModel`.
```
from pydantic import BaseModel, Field

class Request(BaseModel):
    data: str = Field(min_length=1)
```        
#### Validate:
```
request = Request.model_validate(data)
request.model_dump() 
```
#### Add custom validation where necessary by using the field validator decorator.
```
from pydantic import field_validator

@field_validator("text")
@classmethod
def reject_blank(cls, value):
    if not value.strip():
        raise ValueError("Text cannot be blank")
    return value
``` 

This is pretty much the core of how these basic MLOps tools work. How do they actually work together, though? 

### Basic MLOps
The essence of MLOps with FastAPI+Pyndantic is wrapped up in Muyiwa Abidobe's excellent post on MLOps API development. Let's go through it in depth. The steps discussed here are
1. Train the model, 
2. Set-up and write a FastAPI application,
3. Start the application by running in the terminal,
4. Including schemas for documentation. 

Each step is reasonably simple enough, but I'm going to annotate the code to make sure I really understand the workflow here. 

```
# import libraries
from sklearn.datasets import load_iris
from sklearn.ensemble import RandomForestClassifier
import joblib

# Load the dataset
iris = load_iris()
X, y = iris.data, iris.target

# Train the model
model = RandomForestClassifier(n_estimators=100, random_state = 23)
model.fit(X, y)

if __name__ == "__main__":
  # Save the model for use.
  joblib.dump(model, "flower_model.pkl")
```

Nothing too complex here. We're just training a model and obtaining weights. The main output of the code is the `flower_model.pkl` file. The bit for me that is interesting is Muyiwa's `FastAPI` code: I've added it here with my comments and annotations.

```python
from fastapi import FastAPI
from pydantic import BaseModel
import joblib
import numpy as np
import uvicorn

# Load the trained model weights 
# The strength here is that you only really have to load these once.
model = joblib.load("flower_model.pkl")

# FastAPI app - the first major stage of using FastAPI
app = FastAPI()

# Pydantic model to validate input data
# These clearly specify the data schema necessary for the model input. 
# Note the BaseModel type being inherited here: the core of this is to allow stricter parsing features. 
class FlowerFeatures(BaseModel):
    sepal_length: float
    sepal_width: float
    petal_length: float
    petal_width: float

# This is POST endpoint decorator described above. As mentioned, it simply sends information to the model input. 
# Note that the 'path' inside the decorator is literally just that: a URL endpoint.
# 
@app.post("/predict/")
def predict(flower: FlowerFeatures):
    # Prepare the input data
    # This is obtained safely from the Pydantic data schema object. 
    input_data = np.array([[flower.sepal_length, flower.sepal_width, flower.petal_length, flower.petal_width]])

    # Make prediction using the model
    prediction = model.predict(input_data)
    predicted_class = prediction[0]
    
    # point predicted class to flower name
    flower_names = ["Setosa", "Versicolor", "Virginica"]
    flower_name = flower_names[predicted_class]

    return {"prediction": flower_name}

if __name__ == "__main__":
  uvicorn.run("main:app", host = "localhost", port = 8080, reload = True)
```

...*hold on*. There's something missing here. I can send the information to the endpoint. How do I get validated information back?
Checking the quick start guide sort of explains this. 
1. You define a response schema - maybe something like `Prediction(BaseModel)`.
2. You can then add `response_model=Prediction` to the operator, making sure that you return a `Prediction` object in the function.

You probably don't have to do this, but I think this constitutes safe data transfer.

And so, this is the workflow to internalize here. 
1. Set up the model outside the API.
2. Initialize a `FastAPI` object.
3. Define `Pydantic` classes by inheriting from `BaseModel` and maybe some of the functionality provided within the module itself (like `Field`). 
4. Define the `POST` endpoint - a function with an associated `@app.post('path')` decorator and an appropriate  
5. Run using `uvicorn`. 

### Integration into operations 
How might this kind of workflow actually be represented in a full operational ML system? How could I actually do any of this stuff? I'm going to describe a rough plan of how this might all come together in deployment. 

1. **Creating the application**
  * Write some code, build a model, get something that you can use. 
  * Initialize a `FastAPI` object.
  * Create a set of data schemas (`BaseModel` objects) for input and output.
  * Write a function that uses the model prepared in step 1. 
  * Use the `POST` endpoint decorator to convert the function into a routine that sends information into a `html` endpoint and transfers an input to the model. 
  * Run `uvicorn.run` in the main namespace. 
2. **Creating and running the container** 
  * Write a Dockerfile that builds the above source into an image.  
  * Run `docker build -t <container-reference-name> .`
  * Run `docker run` with the necessary inputs.
